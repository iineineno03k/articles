## 課題: 手動だと絶対にサボる

前回の記事で作ったデイリーフィードは、手動で叩けば5分で完成する便利な仕組みだった。だが問題がある。

**手動だと絶対にサボる。** 「あとで読もう」が永遠に来ないのは誰でも知っている。

情報収集ツールは「使う習慣」がないと死ぬ。作って満足→放置が最悪のパターンだ。自分の意志力に頼らず、仕組みで強制的に目に入るようにしたい。メールなら朝のルーティンに自然に入る。

つまりゴールは「Claude Codeでフィード生成→メール送信」を毎朝自動で回すこと。あとは定期実行するだけ……のはずだった。

## 試行1: macOS launchdで全部やる

最初の発想はシンプルだった。macOSの定期実行の仕組み（launchd）で `claude -p` を毎朝叩けばいい。

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN"
  "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>Label</key>
  <string>com.example.daily-feed</string>

  <key>ProgramArguments</key>
  <array>
    <string>/bin/zsh</string>
    <string>/path/to/daily-feed.sh</string>
  </array>

  <!-- 毎日8:00に実行 -->
  <key>StartCalendarInterval</key>
  <dict>
    <key>Hour</key>
    <integer>8</integer>
    <key>Minute</key>
    <integer>0</integer>
  </dict>

  <!-- 環境変数（claude CLIのPATH確保） -->
  <key>EnvironmentVariables</key>
  <dict>
    <key>PATH</key>
    <string>~/.local/bin:/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin</string>
    <key>HOME</key>
    <string>/Users/yourname</string>
  </dict>
</dict>
</plist>
```

launchdの注意点として、`PATH`と`HOME`を明示的に設定する必要がある。launchd経由で起動するとシェルのプロファイルが読み込まれないため、`claude`コマンドのパスが通らない。

初日は動いた。翌日コケた。

### OAuthトークンが約24時間で失効する

Claude Code CLIは`claude login`でOAuth認証する。このトークンには有効期限がある。

ローカルのターミナルで日常的に使っていればトークンは自動リフレッシュされるが、launchdからの定期実行だけに頼っていると、PC起動していなかった日やターミナルを開かなかった日にトークンがリフレッシュされず失効する。出張で2日PCを触らなかったら、帰ってきた朝のフィードが「認証エラー」で空振りしていた。

`claude setup-token`で長寿命トークンを発行する回避策もあるが、根本的に**OAuthに依存する `claude -p` は無人運用に向かない**。

## 試行2: Anthropicクラウドスケジュールタスクに移行

次に目をつけたのが、Claude Codeのクラウドスケジュールタスク機能だ。

`claude.ai/code/scheduled` からGitHubリポジトリを紐づけた環境（Environment）を作り、cron式でプロンプトをスケジュール実行できる。Pro/Maxサブスクリプションの範囲内で追加課金なし。サーバー側で動くのでOAuthトークンの問題が起きない。

設定は以下のような流れだ。

1. `claude.ai/code` でEnvironmentを作成し、GitHubリポジトリを連携
2. `claude.ai/code/scheduled` で「New scheduled task」を作成
3. cron式（`0 8 * * *` = 毎朝8時）とプロンプトを設定
4. プロンプトには「何をして、何が成功か」を自己完結する形で書く

これで毎朝8時にサーバー上でClaude Codeがフィード生成→git pushしてくれる。

フィード生成自体はうまくいった。次はメール送信もサーバー側でやらせようとした。

## 試行3: メール送信が動かない

サーバー側でフィード生成もメール送信も全部やらせようとした。

```bash
# サーバー側でSMTP送信を試みる
curl --ssl-reqd --url 'smtps://smtp.gmail.com:465' \
  --mail-from "$GMAIL_USER" \
  --mail-rcpt "$GMAIL_USER" \
  --user "${GMAIL_USER}:${GMAIL_APP_PASSWORD}" \
  --upload-file - << EOF
Subject: Daily Feed
...
EOF
```

動かない。**サンドボックスのネットワーク制限**で、git操作以外の外部ネットワーク接続がブロックされている。`smtps://smtp.gmail.com:465` への接続がタイムアウトする。

サーバーではメール送信が不可能だと判明した。

## 最終形: サーバー + ローカルの非同期2段構成

3回の試行錯誤を経て、たどり着いた設計はこうだ。

```
[サーバー 毎朝8:00]              [ローカルMac 毎朝8:30]
クラウドスケジュールタスク          launchd
├ 5ソースから生データ取得           ├ git pull --rebase
├ Claude Codeが要約生成           ├ feed.md の存在確認
├ feed.md をコミット              └ Gmail送信（curl SMTP）
└ git push origin main
```

**設計の鍵: 「AIが必要な処理」と「AIが不要な処理」を分離する。**

- **サーバー側（AI処理）**: フィード取得 + AI要約 + git push。OAuthトークン不要で毎日確実に動く
- **ローカル側（非AI処理）**: git pull + メール送信。`claude`コマンドを使わないのでOAuth失効の影響ゼロ

30分の時間差を設けることで、サーバー側の処理完了を待つ。

## 実際のコード

### ローカル側: daily-feed.sh

ローカル側のスクリプトは50行未満の軽量なものだ。`claude`コマンドは一切使わない。

```bash
#!/bin/bash
# daily-feed.sh — ローカルメール送信ジョブ
# サーバー側でfeed.md生成+git pushが完了した後、
# ローカルでpull→メール送信するだけの軽量スクリプト。

set -euo pipefail

PROJECT_ROOT="$(cd "$(dirname "$0")/.." && pwd)"
cd "$PROJECT_ROOT"

DATE_DIR="${1:-$(date +%Y%m%d)}"
FEED_FILE="${PROJECT_ROOT}/feeds/${DATE_DIR}/feed.md"
LOG_DIR="${PROJECT_ROOT}/logs"
LOG_FILE="${LOG_DIR}/daily-feed-$(date +%Y%m%d-%H%M%S).log"

mkdir -p "$LOG_DIR"
exec > >(tee -a "$LOG_FILE") 2>&1

echo "===== daily-feed.sh start: $(date) ====="

# Step 1: git pull でmainを最新化
git pull --rebase 2>&1 || {
  echo "⚠ git pull failed. Trying without rebase..."
  git pull 2>&1 || true
}

# Step 2: feed.mdが存在するか確認
if [ ! -f "$FEED_FILE" ]; then
  echo "✗ feed.md not found: ${FEED_FILE}"
  echo "  サーバー側の生成がまだ完了していない可能性があります。"
  exit 1
fi

# Step 3: メール送信
bash scripts/send-gmail.sh "$FEED_FILE" 2>&1

echo "===== daily-feed.sh complete: $(date) ====="
```

### LaunchAgent plist

ローカルの定期実行設定。ポイントは`RunAtLoad`だ。

```xml
<!-- 毎日8:30に実行（サーバー側feed生成8:00の後にメール送信） -->
<key>StartCalendarInterval</key>
<dict>
  <key>Hour</key>
  <integer>8</integer>
  <key>Minute</key>
  <integer>30</integer>
</dict>

<!-- PC起動時にも実行（8:30を逃した場合の救済） -->
<key>RunAtLoad</key>
<true/>
```

launchdの`StartCalendarInterval`は、PCがスリープ中だった場合、起動後に1回だけ実行してくれる。ただしPCが完全にオフだった場合はスキップされるため、`RunAtLoad`でPC起動時にも実行するようにしている。

### curl SMTPでのGmail送信

```bash
#!/bin/bash
# feed.mdの内容をGmailで送信
# 前提: .envにGMAIL_USER, GMAIL_APP_PASSWORDが設定されていること

FEED_FILE="${1:?Usage: send-gmail.sh <feed.md path>}"
source .env

SUBJECT_RAW="Daily Feed $(date +%Y-%m-%d)"
SUBJECT_B64=$(echo -n "$SUBJECT_RAW" | base64)

curl --silent --url 'smtps://smtp.gmail.com:465' \
  --ssl-reqd \
  --mail-from "$GMAIL_USER" \
  --mail-rcpt "$GMAIL_USER" \
  --user "${GMAIL_USER}:${GMAIL_APP_PASSWORD}" \
  --upload-file - << EOF
From: ${GMAIL_USER}
To: ${GMAIL_USER}
Subject: =?UTF-8?B?${SUBJECT_B64}?=
MIME-Version: 1.0
Content-Type: text/plain; charset=UTF-8

$(cat "$FEED_FILE")
EOF
```

GmailのApp Passwordは、Googleアカウントの2段階認証を有効にした上で生成する。SMTPの外部アプリ用パスワードだ。

## 1週間動かしてみて

この構成で1週間以上安定稼働している。`feeds/`ディレクトリに毎日データが蓄積されていくのを見ると、「仕組みが回っている」実感がある。

朝のメール確認で、昨日何がトレンドだったかが5分でキャッチアップできるようになった。自分の意志力ではなく仕組みに頼った結果だ。

## まとめ

Claude Codeの定期実行でハマるポイントは2つ。

1. **OAuthトークンの失効**: `claude -p` を無人運用するとトークンが切れる。クラウドスケジュールタスクで回避
2. **サンドボックスのネットワーク制限**: サーバー側からSMTP等の外部接続ができない。ローカルとの役割分担で回避

設計原則としては、**「AIが必要な処理」と「AIが不要な処理」を分離する**こと。AI処理はサーバーに任せ、メール送信のような非AI処理はローカルに残す。この分離によって、それぞれの環境の制約を回避できた。

Claude Codeは対話的に使うだけでなく、定期実行で「裏で勝手に動いてくれる仕組み」にすると、日常の情報収集やルーティン作業を自動化できる。ただし定期実行特有のハマりどころがあるので、この記事が参考になれば幸いだ。
