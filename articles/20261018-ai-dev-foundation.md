Claude CodeやCodexに開発を任せるとき、一番大事なのは「どうやってevalするか」を先に決めることだと思っている。

evalの方針さえあれば、AIはそれに従ってE2Eを書いたり、適切な場所にユニットテストを書いたりして、自律的に進められる。逆にevalの方法がないと、AIが作ったものが正しいかを人が毎回読んで確かめるしかなく、任せた意味がなくなる。

この記事では、自分がAIに開発を任せるときに重ねているevalを、順番に書く。例に出すコードは、すべて説明用の架空のものだ。

## 全体の流れ

| 順番 | 何をするか | 何を確かめるか |
|---|---|---|
| 0 | 正解を決める | 何ができていれば「正しい」と言えるか |
| 1 | 人間のレビュー（業務ルールと集約） | ビジネスとして違和感がないか、あるべき設計か |
| 2 | AIのレビュー | セキュリティ、書き方のルールに従っているか |
| 3 | 決定論的な縛り | テストとアーキテクチャのルールを守っているか |
| 4 | ログからの自己改善 | 1〜3の仕組み自体がズレていないか |
| 5 | CI | いつでも動く状態のままか。通ったらマージ |

## 0. 正解を決める

evalの出発点は、「何ができていれば正しいのか」を先に決めることだ。

既存のシステムを置き換える開発なら、互換を保つと決めた範囲では、確かめた既存の挙動を正解として固定できる。新しいものに同じ入力を入れて、同じ結果になるかを確かめればいい。

新規のビジネスで作るなら、そういう正解はない。なので、**ビジネスフローとユースケースを先に出す**。誰が、どういう順番で、何をして、何が起きれば成功か。これが決まっていれば、それをそのままE2Eのシナリオにできるし、細かいルールは適切な場所のユニットテストに落とせる。

ここまでできれば、テストを書くのも、実装するのも、AIに任せられる。`AGENTS.md` には、迷ったら人に聞く前にこの正解を確かめるよう書いておく。

```markdown
## 人間に聞くこと・自分で決めること

人間がレビューするのは、業務ルールと集約だけ。
ほか（設計・テスト・実装・命名・レビュー指摘への対応・作業の順番）は
自分で決めて最後まで進め、決めたことと理由を報告に書く。

迷ったら、聞く前に正解（ユースケース・既存の挙動）を確かめる。
聞いてよいのは、正解を見ても決まらない業務の判断と、
取り消せない操作・外へ出る操作で指示にないものだけ。
```

## 1. 人間のレビューは、業務ルールと集約だけ

全部をAIに任せられるわけではない。AIが自律的に判断できないところと、人間の認知負荷に関わるところは、人が見る必要がある。自分の場合、それが**業務ルールと集約**（業務のまとまりをどこで区切るか）だ。

ここで見るのは、コードの書き方ではない。ビジネスとして違和感がないか、この設計があるべき姿なのか、を整理するところだ。集約の切り方を間違えると、あとから全部に響く。そして、そこが正しいかどうかは、テストでは確かめられない。

なので、業務ルールや集約を新しく書いたり、切り方を変えたりしたら、AIはレビューの依頼を出して止まる。それ以外（既に決まったものを写す、言い直す、細部を足す）は止まらずに進める。

ただ、人間のレビューも決定論的ではない。モデルがもっと賢くなれば、ここも飛ばせるようになるかもしれない、とは思っている。

## 2. AIのレビュー

次のevalは、AIによるレビューだ。人が見ない代わりに、セキュリティや書き方のルールに従っているかを、AIに見させる。

ポイントは、観点ごとにレビュー役を分けることだ。

| 観点 | 見るもの |
|---|---|
| 正しさ | ユースケースやルールに対するテストの抜け、エラー処理、同時実行 |
| セキュリティ | 認可、入力の検査、インジェクション、秘密情報、ログへの漏洩 |
| パフォーマンス | SQL、トランザクションとロック、メモリ |
| 設計と規約 | 層と依存の向き、置き場所、命名などの書き方のルール |

各観点は自分の観点だけを見て、他の観点の問題は書かない。全部を1つに見させると、指摘が浅く広くなる。Claude Codeでは観点ごとにサブエージェントを立てて並列で回している。

もう一つ、**作った会話とは別の文脈でレビューさせる**こと。作ったAIに自分でレビューさせると、自分の前提をそのまま信じて見落とす。レビュー役には、自分がどう考えて作ったかを渡さず、差分と正解の場所だけを渡す。結論を渡すと、レビュー役はその結論を確かめ直すだけになる。

回す回数も決めておく。PRを出す前と、まとまった変更を足したあとの1回ずつ。小さな修正のたびに回すと、トークンが跳ね上がる。

## 3. 決定論的な縛り

AIのレビューも、結局は確率的だ。見落とすときは見落とす。

なので、守ってほしいルールは、**Markdownに書くのではなく、テストで縛る**。

たとえば、オニオンアーキテクチャ（クリーンアーキテクチャも同じ考え方）を採用しているなら、依存は外側から内側への一方向で、内側のドメイン層は外側のインフラ層に依存しない、というルールがある。これを規約の文書に書くだけだと、AIはたまに破る。テストにしておけば、破った瞬間に落ちる。下の例は、そのアーキテクチャを採っている前提のものだ。

```go
// 例：ドメイン層がインフラ層を import していたら落とす
func TestDomainDoesNotDependOnInfra(t *testing.T) {
	const infra = "example.com/app/internal/infra"
	out, err := exec.Command("go", "list", "-f", `{{join .Imports "\n"}}`, "./internal/domain/...").Output()
	if err != nil {
		t.Fatal(err)
	}
	for _, imp := range strings.Split(string(out), "\n") {
		if imp == infra || strings.HasPrefix(imp, infra+"/") {
			t.Fatalf("domain が infra に依存している: %s", imp)
		}
	}
}
```

この例で縛れるのは直接のimportだけだが、それでも、テストにしたルールについては、AIは破った形のままでは実装を通せなくなる。文書は「なぜそうするか」を書く場所で、守らせるのはテストとlintの仕事、と分けている。

## 4. ログからの自己改善

ここまでのeval（正解、人間のレビュー、AIのレビュー、決定論的な縛り）は、使っていると必ずズレが出る。人が同じ修正を何度も言っている、判断の要らないところで止まっている、関係ないファイルを読み込んでトークンを食っている、といったものだ。

これを人が覚えておいて直すのは続かないので、会話ログを集めて、AIに直させている。

- Claude CodeとCodexの会話ログ（サブエージェントとのやり取りも含む）を、hookで自動的に集める。ログには秘密情報が入り得るので、保存先と、会話に何を貼らないかを先に決めておく。
- 作業が終わるたびに、その作業のログを分析させる。修正指示の数、トークンの量、どこで膨らんだか。見直しが必要なら、`AGENTS.md`やスキルやサブエージェントの定義を直して、同じPRに別のコミットで載せる。
- この振り返りをせずにマージしようとすると、hookが止める。

2の「レビューを回す回数」も、このログの分析から決まったものだ。

## 5. CIで確かめて、マージ

最後はCIだ。1〜4を通ったものが、いつでも動く状態のままかをCIで確かめ、通ったらマージする。

ここまでevalが重なっていれば、人がPRをApproveするのを待つ必要はない。CIが通ったらAIが自分でマージして、結果を報告する。

## まとめ

AIに開発を任せられるかどうかは、AIの賢さより、evalの方法を先に決められているかで決まる。

- 正解を決める（既存の挙動、またはビジネスフローとユースケース）
- 人間は業務ルールと集約だけを見る
- AIに観点別のレビューをさせる
- 守らせたいルールはテストで縛る
- ログから仕組みそのものを直させる
- CIで確かめてマージする

evalの方法さえ決まっていれば、その先はAIが自分で進められる。
